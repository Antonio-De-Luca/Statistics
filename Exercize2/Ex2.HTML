End-to-end model

The simplified wallet pipeline

Wallets combine several standards because no single algorithm performs secure backup, hierarchical organization, public-key operations, hashing and typo detection equally well.

1

Mnemonic

BIP-39

Encodes entropy and a small checksum as a human-readable sequence of words.

2

Seed

PBKDF2-HMAC-SHA512

Converts the normalized mnemonic and optional passphrase into a deterministic 512-bit seed.

3

Private key

BIP-32 / BIP-44

Derives a tree of extended keys and selects an Ethereum account through a standard path.

4

Public key

secp256k1

Computes a public curve point from the private scalar using one-way scalar multiplication.

5

Hash

Keccak-256

Hashes the uncompressed public-key coordinates to a 256-bit digest.

6

Address

Last 20 bytes

Keeps the rightmost 160 bits and represents them as 40 hexadecimal characters with a 0x prefix.

7

Checksum case

EIP-55

Uses letter capitalization to add error detection without changing the underlying 20-byte address.

Roles and purposes

Six standards and primitives

Mnemonic encoding + seed generation

BIP-39

BIP-39 first maps cryptographically random entropy plus checksum bits into words selected from a 2048-word list. It then derives a 64-byte seed using PBKDF2-HMAC-SHA512 with 2048 iterations.

seed = PBKDF2-HMAC-SHA512(mnemonic, "mnemonic" + passphrase, 2048)
Hierarchical key derivation

BIP-32

BIP-32 turns a seed into a master private key and chain code, then deterministically derives child extended keys. A single backup can reproduce many accounts and addresses.

  • Hardened derivation protects parent relationships.
  • Non-hardened derivation supports public child derivation.
  • The chain code is derivation metadata, not an address.
Path organization

BIP-44

BIP-44 assigns meaning to levels in the BIP-32 tree. A commonly used Ethereum path is:

m / 44' / 60' / 0' / 0 / 0

The fields represent purpose, coin type, account, change and address index. The apostrophe marks hardened derivation.

Public-key cryptography

secp256k1

The private key is a scalar in the curve's valid range. The public key is the point obtained by multiplying the curve's generator point by that scalar.

Q = d x G

Computing Q from d is efficient. Recovering d from Q is intended to be computationally infeasible. Ethereum also uses this key relationship for ECDSA signatures.

Cryptographic hashing

Keccak-256

Ethereum hashes the 64-byte uncompressed public-key coordinates, excluding the 0x04 serialization prefix when that prefix is present.

address = rightmost_20_bytes(Keccak-256(public_key[1:]))

Hashing compresses the public key and produces a fixed-size, avalanche-sensitive identifier.

Checksum encoding

EIP-55

EIP-55 hashes the lowercase hexadecimal address and uses selected hash bits to decide whether each alphabetic address character is uppercase or lowercase.

Capitalization changes the textual representation, not the underlying 160-bit address. It detects many accidental typing errors but is not authentication or encryption.

Do not conflate these operations

Five different concepts

Key generation

Creates new secret material from high-quality randomness. In BIP-39, initial entropy is generated before being encoded as words.

Key derivation

Deterministically computes keys from an existing seed or parent key. The same input and path reproduce the same child key.

Public-key cryptography

Establishes a mathematically linked private/public key pair and enables digital signatures without revealing the private key.

Hashing

Maps arbitrary input to a fixed-size digest. It is one-way, deterministic and designed to resist collisions and preimages.

Checksum and encoding

Encoding changes representation. A checksum adds limited error detection. Neither supplies secrecy or proves ownership.

Statistical properties

What security claims mean numerically

Cryptographic outputs are designed to appear statistically uniform, but their effective security depends on output size, attack model and the entropy of the original secret.

128 bits

Common entropy for a 12-word BIP-39 mnemonic. Four checksum bits produce 132 total bits, split into twelve 11-bit word indices.

256 bits

Common entropy for a 24-word mnemonic. Eight checksum bits produce 264 total bits, split into twenty-four word indices.

256 bits

Keccak-256 digest length. An ideal 256-bit hash offers about 256-bit preimage resistance and 128-bit generic collision resistance.

160 bits

Ethereum externally owned account address length after truncating the public-key hash to 20 bytes.

Uniformity and probability

Expected behavior

  • Securely generated private keys are approximately uniform over the valid secp256k1 scalar range.
  • A one-bit input change should unpredictably alter about half of a cryptographic hash's output bits on average.
  • For an ideal 160-bit address space, a targeted preimage search requires roughly 2^160 trials.
  • Generic collisions become plausible around 2^80 samples because of the birthday bound.
  • Truncation from 256 to 160 bits reduces address-level collision security but does not expose the private key.

Entropy is the foundation

A formally correct pipeline cannot repair weak randomness. Human-chosen words are not a safe substitute for wallet-generated entropy. A BIP-39 passphrase also creates a different valid wallet, so losing or mistyping it changes every derived key.

Temporal context

A short cryptographic timeline

1977

RSA

RSA demonstrates practical public-key encryption and digital signatures using integer factorization.

2001

SHA-2

The SHA-2 family, including SHA-512, is standardized. SHA-512 later becomes part of BIP-39 and BIP-32 constructions.

2012

BIP-32

Hierarchical deterministic wallets organize many keys under one master seed and chain code.

2013

BIP-39

Mnemonic sentences provide a human-manageable encoding and a deterministic seed-generation procedure.

2014

BIP-44

A multi-account path structure gives BIP-32 trees standardized purpose, coin and account levels.

2015

SHA-3

NIST publishes FIPS 202, standardizing functions based on the Keccak design.

2016

EIP-55

Ethereum gains an optional mixed-case checksum representation for hexadecimal addresses.

Important distinction

SHA-512, Keccak-256 and SHA3-256

Function Family and role Wallet relevance
SHA-512 A 512-bit member of the SHA-2 family, standardized before SHA-3. Used inside HMAC and PBKDF2 by BIP-32 and BIP-39. It is not the hash used to form an Ethereum address from a public key.
Keccak-256 A 256-bit function based on the Keccak design as used before final SHA-3 standardization. Used by Ethereum for public-key-to-address derivation and many protocol-level hashing operations.
SHA3-256 The standardized FIPS 202 SHA-3 function, also based on Keccak. It is not interchangeable with Ethereum's Keccak-256 because the padding and domain-separation conventions differ.

Why not one algorithm for everything?

These components solve different problems. BIP-39, BIP-32 and BIP-44 manage deterministic secrets and account organization. secp256k1 creates a one-way private/public relationship and supports signatures. Keccak-256 compresses data into fixed-size digests. EIP-55 overlays limited typo detection on hexadecimal text.

Reusing one primitive outside its designed role would remove useful security properties rather than simplify the system. A hash is not a signature scheme, a checksum cannot protect a private key, and an elliptic curve does not provide a human-friendly backup format.

Wallet software

What users observe in practice

Recovery phrase

Wallets may expose a recovery phrase during setup or backup. Internally, compatible wallets can use it to reproduce a seed and derive accounts. Product details can differ, so compatibility should not be assumed solely from a similar interface.

Multiple accounts

Choosing "add account" often derives another child key rather than creating an unrelated backup. The exact path and account discovery procedure determine whether another wallet finds the same accounts.

The visible address

Apps usually display the EIP-55 mixed-case form. Ethereum address comparison is based on the underlying 20 bytes, while the case pattern helps interfaces detect some transcription mistakes.
